# 开发过程与人工审查

## 1. 协作方式

项目按照业务域拆分实现，再逐项联调与验收。AI 主要用于生成基础骨架、重复度较高的界面代码、接口草稿和测试用例；业务规则、数据结构、异常处理、视觉取舍和最终验收由人工审查确认。

对外文档只保留需求结论、设计说明、操作方式和验证结果，不保留原始过程提示词、个人环境信息或内部工作记录。

## 2. 需求组织

开发时采用“总目标 + 业务规则 + 页面约束 + 验收条件”的分层写法：

1. 明确系统边界：本地离线运行、PC 端使用、真实业务闭环。
2. 把输血规则写成可执行条件，包括 ABO/Rh 相容性、Rh 阴性限制、四项发血核对和 FEFO 推荐。
3. 约束页面一致性，包括医疗蓝主色、低饱和背景、组件图标、统一操作列和路由加载兜底。
4. 用自动化测试验证登录、越权、主流程、审计日志和数据库注释完整性。

## 3. 人工介入与修改原因

| 介入点 | 发现的问题 | 人工处理 | 修改原因 |
| --- | --- | --- | --- |
| 页面加载白屏 | 部分路由切换时整页失去反馈 | 使用路由懒加载、`Suspense`、`RouteLoading` 和路由级错误兜底 | 加载异常时仍需保留可恢复界面 |
| 图标比例不一致 | 手写 SVG 在不同字号下变形 | 统一使用 Element Plus 组件图标 | 组件图标尺寸和视口更稳定 |
| 操作按钮换行 | 库存管理等页面操作列容易掉到第二行 | 抽出 `TableActions` 统一渲染并折叠次要操作 | 保持多分辨率下布局一致 |
| 视觉过重 | 背景与装饰饱和度偏高 | 降低背景深度、纹理浓度和动效强度 | 符合医疗业务系统的克制感 |
| 业务按钮反馈不足 | 关键操作与普通按钮区分不明显 | 使用渐变、组件图标和适度的悬停反馈 | 明确操作优先级，同时避免干扰录入 |
| 越权证据不足 | 仅有前端菜单隐藏，缺少后端验证 | 增加医生、护士访问系统管理接口的 403 测试 | 权限必须由后端强制校验 |
| 审计证据不足 | 发血日志已写入但缺少断言 | 按发血记录号反查操作日志 | 证明真实操作与审计记录可对应 |
| 数据库说明缺失 | SQLite 不保存原生表字段注释 | 建立 `schema_comment` 字典表并生成数据库字典 | 方便查看字段含义和答辩讲解 |
| 验收入口分散 | 需要分别启动服务和执行测试 | 增加一条命令的验收自检脚本 | 降低现场演示步骤和环境影响 |

## 4. 使用边界

- 系统运行时不调用外部大模型，也不依赖网络 API。
- FEFO 推荐、临期提醒、低库存提醒和超时提醒均为可解释的规则计算。
- 业务状态由数据库和后端规则决定，前端不自行编造完成状态。
- 费用管理、自备血专项工作流和外部 HIS/LIS 实时接口属于明确的系统边界。

## 5. 验证结果

在项目根目录执行：

```powershell

```

脚本会自动运行 pytest、创建临时数据库、启动临时后端并执行 HTTP 主流程。当前结果：

## 6. 演示建议

- 先讲业务闭环，再讲技术实现，不从页面组件开始罗列。
- 重点展示一次“不相容配血被后端拦截”。
- 用现场生成的发血记录号查询审计日志，证明操作与日志来自同一条真实数据。
- 主动说明自备血、费用和外部接口的边界。
- 讲人工介入时重点说明“为什么改”，例如白屏涉及故障恢复，操作列涉及长期维护成本。
